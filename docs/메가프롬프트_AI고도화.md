# 메가프롬프트: AI 로직 고도화 (비용, 응답 명확성, 전문가 점검)

작성 2026-10-27. 다른 세션에서 이 파일 전체를 첫 메시지로 붙여 넣어 시작한다.

---

## 0. 너의 역할과 진행 방식

너는 이 저장소(그래고, Expo 앱 + Supabase Edge Functions + Gemini)의 AI 로직을 오너와 같이 고도화한다.
목표는 세 가지다.

1. 토큰과 비용을 줄인다.
2. AI 응답을 더 명확하고 일관되게 만든다.
3. LLM 서비스 전문가 입장에서 이 서비스에 필요한 것을 찾아 제안한다.

진행은 반드시 아래 단계를 따른다. **단계마다 오너 승인 없이 다음 단계로 넘어가지 않는다.**

| 단계 | 하는 일 | 끝에 오너에게 보여 줄 것 |
|---|---|---|
| 1. 파악 | 코드와 데이터를 읽고 지금 구조를 지도로 만든다 | AI 호출 지도 한 장 |
| 2. 측정 | 실제 토큰과 비용을 잰다. 추정과 실측을 구분한다 | 비용표 |
| 3. 진단 | 비용, 명확성, 그 밖의 문제 후보를 근거와 함께 나열한다 | 후보 목록(효과, 위험, 작업량) |
| 4. 합의 | 오너와 상의해 할 항목과 순서를 고른다 | 확정 계획 |
| 5. 실행 | 항목 하나씩 고치고, 항목마다 전후를 잰다 | 항목별 전후 비교 |
| 6. 마무리 | 평가 재실행, 문서 갱신, 커밋 | 결과 요약 |

작업 원칙은 `~/.claude/CLAUDE.md`와 저장소 `AGENTS.md`를 따른다. 특히:
- 가정은 명시하고, 해석이 여러 개면 전부 제시한다.
- 요청하지 않은 기능은 넣지 않는다. 변경된 모든 줄이 합의된 항목과 연결돼야 한다.
- 오너에게 하는 말은 쉬운 한국어로, 결론부터 쓴다. 오너는 개발자가 아니다. 전문 용어는 처음 나올 때 한 줄로 풀어 쓴다.
- 질문은 선택지로 묻는다(AskUserQuestion). 추천안이 있으면 첫 번째에 두고 이유를 쓴다.
- `ai-failure-hunt` 스킬이 있으면 3단계와 5단계에서 불러 쓴다(대리지표 의심, 고치기 전에 재기, A/B로 기여도 분리).

## 1. 서비스 배경 (먼저 읽을 것)

- 이름 그래고. 목표를 정하면 달성할 때까지 하게 만드는 앱. 1차 분야는 영어 회화, 대상은 '가짜 초보' 성인.
- 하루 흐름: 오늘의 이유 쓰기 → 학습(A 복습 퀴즈 → B 상황 대화 → C 복습) → AI 회고. 포기하려 하면 반성문.
- 기획: `docs/기획서.md`, `docs/학습세션_결정안.md`, `docs/학습콘텐츠.md`, `docs/결정로그.md`
- 최근 결정: `reports/상황 대화학습 피드백 개선.md` (교정 피드백을 단서 → 패턴 단계로, 2026-10-22)
- 운영 현황: `docs/HANDOFF.md`, `WORK_LOG.md`

## 2. 지금 AI 구조 (2026-10-27 확인한 사실. 1단계에서 다시 확인한다)

| 함수 | 하는 일 | 모델 등급 | 프롬프트 파일 |
|---|---|---|---|
| goal-setup | 목표 정하기 대화. 이유, 장소, 역할, 상대, 할 일을 채운다 | main | `_shared/prompts/goal-setup.ts` (약 4KB) |
| lesson-turn | 상황 대화 턴, 시작 턴, 변형 에피소드 생성. 호출 지점 3곳 | main | `_shared/prompts/lesson-turn.ts` (약 13KB) |
| review-quiz | 복습 문제 내기와 채점 | light | `_shared/prompts/review-quiz.ts` (약 5KB) |
| retro | 하루 끝 회고 | main | `_shared/prompts/retro.ts` (약 2KB) |
| reflection | 포기 때 반성문 | main | `_shared/prompts/reflection.ts` (약 4KB) |
| delete-account | AI 없음 | | |

- 경로는 모두 `supabase/functions/` 아래다.
- 모델: main `gemini-3.8-flash`, light `gemini-3.5-flash-lite`. `_shared/config.ts`. thinking_level은 main low, light minimal.
- 전송: `_shared/gemini.ts`. Gemini Interactions API. 출력 상한 기본 1024 토큰.
- 검증: 출력이 JSON 스키마나 내용 검사(해요체, 정답 유출 등)를 통과 못 하면 문제를 적어 **1회 재요청**한다. 재요청도 비용이다.
- 상한: 사용자당 하루 150회, 목표 설정 30회, 전체 하루 20000회. `_shared/usage.ts`, `_shared/rules.ts`.
- 기록: 모든 호출(재시도 포함)이 `public.ai_usage`에 남는다. 열: fn, prompt_version, model, input_tokens, output_tokens, latency_ms, ok, day.
- 맥락: `_shared/context.ts`, `_shared/memory.ts`가 프롬프트에 넣을 이력(아는 표현 최근 40개, 대화 등)을 만든다.
- 평가: `evals/run.ts`, 케이스 `evals/cases/*.json`, 판정 기준 `evals/judge/*.md`. `GEMINI_API_KEY=<키> npm run eval`. 결과는 `evals/report.md`. 약 250회 호출. 실제 모델 평가는 아직 한 번도 안 돌렸다.
- 테스트: `npx deno test -A supabase/functions`(deno가 PC에 없으면 npx로), `npm test`, `npm run typecheck`, `npx expo lint`, `npm run check:static`, `npx supabase test db`.

운영:
- Supabase 프로젝트 ref `tdeogkrelzyilpqtrptu`. CLI는 연결돼 있다. 운영 데이터는 오너 확인 없이 쓰거나 지우지 않는다. 읽기 조회는 해도 된다.
- Gemini 키는 Supabase secrets에만 있다. 로컬 eval을 돌리려면 오너에게 키를 환경변수로 넣어 달라고 한다. 키를 채팅에 받지 않는다.
- 운영 실호출은 2026-10-27 기준 확인용 몇 건뿐이다. 실측 데이터가 적으면 그렇다고 말하고 eval이나 스크립트 호출로 보충한다.

## 3. 단계별 지시

### 1단계: 파악
- 위 5개 함수의 handler, core, prompt, context, memory를 읽는다.
- **AI 호출 지도**를 만든다. 함수마다 아래를 표로 정리한다.
  - 언제 불리나(화면, 하루에 몇 번)
  - 입력에 무엇이 들어가나(시스템 프롬프트, 상황, 이력, 대화 몇 줄)
  - 출력 모양(스키마)과 출력 상한
  - 서버가 출력 뒤에 하는 처리(자르기, 덮어쓰기, 재요청 조건)
- 사용자 한 명의 **하루 호출 수**를 흐름대로 센다. 정해진 학습 분(5~30분)에 따라 달라지면 구간으로 쓴다.
- 여기서 끝내고 지도를 오너에게 보여 준다.

### 2단계: 측정
- 비용 단가는 기억으로 쓰지 않는다. Google 공식 가격 페이지를 열어 모델별 입력, 출력, 캐시 단가를 확인하고 출처와 확인 날짜를 적는다.
- 토큰 수는 세 가지 출처를 구분한다. 실측(ai_usage), 실험(eval이나 스크립트 호출), 추정(글자 수 기반). 표에 출처 열을 둔다.
- 결과 표:
  - 함수별 1회 평균 입력, 출력 토큰
  - 사용자 1명 하루 비용, 한 달 비용(주 5일 기준)
  - 사용자 100명, 1,000명일 때 한 달 비용
  - 재요청 비율과 그 비용
  - 응답 시간(latency) 중앙값과 느린 쪽
- 비용이 가장 큰 곳 상위 3개를 한 줄씩 짚는다.

### 3단계: 진단
아래는 **확인할 가설**이다. 결론이 아니다. 각각 코드나 데이터로 맞는지 확인하고, 아니면 버린다. 여기 없는 것도 찾는다.

비용:
- 매 턴 같은 긴 시스템 프롬프트를 다시 보낸다. Gemini 컨텍스트 캐싱(암시적, 명시적)이나 Interactions API의 대화 상태 저장으로 줄일 수 있나. 공식 문서로 조건(최소 토큰, 단가, 보관 시간)을 확인한다.
- 이력(아는 표현 40개, 대화 전체)이 필요 이상으로 길다. 몇 개, 몇 줄이면 품질이 유지되나.
- main 모델이 꼭 필요하지 않은 호출이 있다(예: 시작 턴, 변형 에피소드, 회고 일부). light로 내려도 품질이 유지되나.
- thinking_level, 출력 상한이 과하거나 부족하다.
- 재요청이 자주 일어나는 검사가 있다. 프롬프트를 고쳐 처음부터 통과시키면 재요청 비용이 준다.
- AI 없이 서버 규칙으로 할 수 있는 일을 AI가 한다(예: 형식 검사, 고정 문구).
- 미리 만들어 둘 수 있는 것을 매번 만든다(예: 변형 에피소드, 상황 시작 문장).

명확성:
- 프롬프트 안 규칙끼리 충돌한다(예: 같은 목표 형태 재적용 vs 예산 0일 때 쉬운 질문).
- 출력 스키마 필드 설명이 모호해서 모델이 다르게 해석한다.
- 한국어 코치 말투(합쇼체, 짧은 문장) 규칙이 함수마다 다르다.
- 판정(natural / needs_correction 등) 경계 사례가 eval에 없다.
- 프롬프트 버전(`PROMPT_VERSION`)과 eval 결과가 연결돼 기록되나.

그 밖에 전문가로서 볼 것:
- 실패 대응: Gemini 장애, 느린 응답, 상한 초과 때 사용자에게 무엇이 보이나. 조용히 실패하는 곳은 없나.
- 품질 감시: 운영에서 품질이 떨어지는 걸 어떻게 알 수 있나. 신고(report_ai_text)와 ai_usage로 볼 수 있는 지표.
- 보안: 프롬프트 주입 방어(`<learner_message>` 데이터 처리)가 모든 함수에 같은가.
- 개인정보: 프롬프트에 필요 이상의 개인 정보가 들어가나. 처리방침의 국외 이전 항목과 실제 전송 항목이 맞나.
- 남용: 상한 숫자(150, 30, 20000)가 비용 기준으로 맞나. 한 사용자가 하루 상한을 다 쓰면 얼마인가.
- 비용 상한: Google Cloud 예산 알림, 지출 상한이 설정됐는지 오너에게 확인한다.

결과물: 후보 목록 표. 열은 번호, 분류(비용, 명확성, 운영), 문제, 근거(파일:줄 또는 수치), 예상 효과(가능하면 숫자), 품질 위험, 작업량(작음, 보통, 큼).

### 4단계: 합의
- 후보 목록을 효과 대비 작업량 순으로 정렬해 보여 준다.
- 추천 묶음 1개를 제안한다. 이유를 두세 문장으로 쓴다.
- 오너가 고른 항목마다 **성공 기준**을 정한다. 예: "lesson-turn 1회 입력 토큰 30% 감소, eval 합격선 유지".
- 짧은 실행 계획을 쓴다: `1. [항목] → 검증: [확인 방법]`.
- 오너가 승인하면 5단계로 간다.

### 5단계: 실행
항목마다 이 순서를 지킨다.
1. 고치기 전 수치를 잰다(토큰, eval 점수, 재요청 비율).
2. 동작을 바꾸는 변경이면 실패하는 테스트나 eval 케이스를 먼저 추가하고 실패를 확인한다.
3. 고친다. 프롬프트를 바꾸면 `PROMPT_VERSION`을 올린다.
4. 다시 잰다. 전후 표를 남긴다. 효과가 없거나 품질이 떨어지면 되돌리고 보고한다.
5. 테스트 전체(deno, npm test, typecheck, lint, check:static, 필요하면 supabase test db)를 돌린다.
6. 항목 하나가 끝나면 커밋한다. 메시지 끝에 저장소 규칙의 Co-Authored-By 줄을 붙인다.

운영 배포(`supabase functions deploy`, `db push`)는 항목별로 오너에게 묻고 한다.

### 6단계: 마무리
- 실제 모델로 `npm run eval`을 돌려 합격선을 확인한다. 못 넘으면 출시를 막는 문제라고 분명히 말한다.
- `evals/sample-for-human.md` 표본 중 바뀐 함수의 것을 오너가 읽을 수 있게 고른다.
- `docs/결정로그.md`에 결정을, `WORK_LOG.md`에 작업 기록을 추가한다.
- 최종 보고: 한 달 비용 전후, 바뀐 항목, 남은 후보, 검증하지 못한 것.

## 4. 하지 말 것
- 가격, 모델 이름, API 기능을 기억으로 단정하지 않는다. 공식 문서를 확인한다.
- 측정 없이 "줄어들 것이다"라고 보고하지 않는다.
- 오너가 고르지 않은 항목을 같이 고치지 않는다. 발견하면 목록에 추가만 한다.
- 운영 DB에 쓰기, 운영 배포, 비용이 큰 대량 호출(eval 2회 이상 등)은 미리 묻는다.
- `ios/`, `android/` 폴더를 만들거나 고치지 않는다.

## 5. 첫 메시지

1단계부터 시작한다. 시작할 때 오너에게 두 가지만 묻는다.
1. 이번 작업에서 가장 중요한 것(비용, 응답 품질, 둘 다)
2. 실제 Gemini 호출로 측정해도 되는지와 대략의 예산(예: 이번 작업 전체 1만 원 이하)
