# 메가프롬프트: 디자인 고도화 (처음 쓰는 사람의 이해, 데이터에 따른 위계)

작성 2026-10-27. 다른 세션에서 이 파일 전체를 첫 메시지로 붙여 넣어 시작한다.

---

## 0. 너의 역할과 목표

너는 이 저장소(그래고, Expo/React Native 앱)의 화면 디자인을 오너와 같이 고도화한다. 풀 문제는 두 가지다.

1. **처음 쓰는 사람이 앱이 어떻게 돌아가는지 모른다.** 별도 튜토리얼 없이, 쓰면서 그 자리에서 바로 알게 해야 한다.
2. **데이터에 따라 디자인이 달라지지 않는다.** 무엇이 중요한지, 무엇을 강조하는지가 화면에 드러나지 않는다. 실제 출시 앱 레퍼런스를 근거로 고친다.

세 스킬을 순서대로 쓴다.

| 단계 | 스킬 | 결과물 | 끝나면 |
|---|---|---|---|
| A | `first-run-walkthrough` | 처음 쓰는 사람이 막히는 곳 목록 | 오너 확인 |
| B | `uiux-blocks` | 레퍼런스 실측, 블록 어휘, 화면별 최우선, HTML 데모 | 오너가 데모 보고 합의 |
| C | `ui-ux-pro-max`, `mobile-app-ui-design` (프로젝트 스킬) | 합의안의 규칙 누락 점검 | 오너 확인 |
| D | 구현 | 합의된 것만 코드 반영, 재촬영, 검증, 커밋 | 결과 보고 |

**단계마다 오너 승인 없이 다음 단계로 넘어가지 않는다.** 각 스킬의 자체 절차가 있으면 그 절차를 따르고, 이 문서는 순서와 입력, 출력만 정한다.

작업 원칙:
- `~/.claude/CLAUDE.md`, 저장소 `AGENTS.md`를 따른다. 가정은 명시하고, 해석이 여러 개면 전부 제시한다. 합의 안 된 변경은 하지 않는다.
- 오너는 개발자가 아니다. 쉬운 한국어로 결론부터 쓴다. 시각 판단이 필요한 것은 말보다 그림(스크린샷, HTML 데모)으로 보여 준다.
- 질문은 선택지로 묻는다(AskUserQuestion). 화면 시안 비교는 preview를 쓴다.
- 화면 문구를 새로 쓰면 `copy-tone` 스킬을 먼저 불러온다(화면 문구 유형).

## 1. 서비스 배경 (먼저 읽을 것)

- 그래고: 목표를 정하면 달성할 때까지 하게 만드는 앱. 안 하면 끈질기게 연락하고 말로 긁는다. 격려는 아낀다. 1차 분야는 영어 회화, 대상은 '가짜 초보' 성인.
- 하루 흐름: 정한 시각에 시작 → 오늘의 이유 쓰기 → 학습(A 복습 퀴즈 → B 상황 대화 → C 복습) → AI 회고 → 완료. 늦으면 1분마다 독촉. 쿠폰으로 하루 쉴 수 있다. 포기는 24시간 대기와 반성문.
- 첫 학습은 목표를 만든 **다음 날**부터 열린다.
- 문서: `docs/기획서.md`(정의, 원칙, 감정 경로), `docs/화면구성.md`, `docs/학습세션_결정안.md`, `docs/용어집.md`, `docs/결정로그.md`
- 지난 UX 작업: `docs/UX고도화_갭분석.md`(12절이 반영 결과), `docs/메가프롬프트_UX고도화.md`. 규칙 위주(대비, 터치, 문구, 모션, 설정 구조)로 이미 많이 고쳤다. **같은 지적을 반복하지 말고 그 결과 위에서 시작한다.**
- 디자인 체계: `src/lib/theme.ts`, `docs/design-system.html`. 아이보리 `#F3EFE6`, 검정 `#111111`, 빨강 `#C8201A` 세 색. 빨강은 독촉, 이탈, 포기에만. 평면, 2px 검정 테두리, Noto Sans KR 굵은 계열, 큰 숫자. 학습 B단계만 다크.
- 현재 화면 캡처: `docs/화면상태/` 169장(화면-상태별). 캡처 스크립트: `scripts/e2e/ui-states.py`. 상태 정의: `docs/화면상태.md`.
- 부품: `src/components/`(ui.tsx, Composer, Coachmark, goal/Chip 등). 처음 안내 코치마크는 홈에 있다(`seenTips`).

## 2. 이미 확인한 문제 (2026-10-27, 출발점일 뿐이다. A, B에서 다시 확인한다)

홈, 첫 학습 전 (`docs/화면상태/home-normal-before_first.png`)
- 가장 큰 글씨가 "0분"이다. 새 사용자에게 의미 없는 숫자가 가장 강조돼 있다.
- "21시간 59분"(첫 학습까지)이 "0분"과 같은 크기라 둘의 무게가 같다. 이 사람에게 중요한 것은 "내일 몇 시에, 무엇을 하나"다.
- "남은 쿠폰 3장"을 설명하지 않는다.
- 이번 주 달력이 빈 칸 7개다. 무엇이 채워지는지 말하지 않는다.
- 하루 학습이 어떤 단계로 진행되는지 보여 주는 곳이 없다.

목표 정하기 2/3 (`docs/화면상태/goal-new-normal-plan.png`)
- 기간, 시작 시각, 시작 분, 하루 학습이 모두 같은 `- 숫자 +` 상자다. 결정의 무게가 구분되지 않는다.
- 기간은 상자와 칩이 같은 값을 두 번 받는다.
- 칩, 입력창, 상자가 모두 검정 테두리 둥근 모양이다. 누르는 것, 입력하는 것, 보여 주는 것의 생김새가 같다.

이미 고친 것(2026-10-27): 목표 정하기 빠른 답 칩을 테두리 없는 채움 모양으로 바꿨다(`Chip` `reply`). 입력창 안내 문구를 연하게 했다. 웹 스크롤바를 숨겼다.

## 3. 단계별 지시

### A. 처음 쓰는 사람의 막힘 찾기 (`first-run-walkthrough`)
- 페르소나: 수능 뒤 영어를 놓은 30대 직장인. 앱 설명을 읽지 않고 설치했다.
- 경로 세 개를 따라간다.
  1. 설치 → 가입 → 목표 정하기 → 홈(첫 학습 전)
  2. 다음 날 첫 학습: 시작 → 이유 → A → B → C → 회고 → 완료
  3. 사흘째: 늦어서 독촉 받음, 쿠폰 사용, 기록 탭 보기
- 화면마다 네 질문으로 판정한다. 무엇을 할 수 있는지 아는가. 무엇을 해야 하는지 아는가. 한 일의 결과를 아는가. 다음에 무슨 일이 일어나는지 아는가.
- 앱을 직접 띄워 보려면 2절 실행법을 쓴다. 띄울 수 없으면 `docs/화면상태/` 캡처로 한다.
- 결과물: 표(경로, 화면, 막히는 지점, 사용자가 모르는 것, 심각도, 근거 캡처). 심각도는 "포기로 이어짐 / 헤맴 / 사소함".
- 이 목록은 B단계의 입력이다.

### B. 레퍼런스로 위계 정하기 (`uiux-blocks`)
- 스킬 절차대로 앱스토어에서 실제 스크린샷을 내려받아 눈으로 보고 실측한다. 기억으로 레퍼런스를 설명하지 않는다.
- 레퍼런스 후보(스킬이 실제로 보고 고른다): 학습 진행과 첫 안내는 듀오링고, 스픽, 케이크. 숫자와 상태 위계는 토스, 애플 피트니스. 습관과 약속은 Streaks, Forest, 챌린저스.
- 볼 것:
  - 같은 화면이 사용자 상태(첫날, 진행 중, 놓침, 완료)에 따라 무엇을 키우고 무엇을 숨기나
  - 처음 보는 요소(쿠폰, 연속 일수, 빈 달력)를 그 자리에서 어떻게 설명하나
  - 누르는 것, 입력하는 것, 정보를 보여 주는 것의 모양 차이
  - 큰 숫자 하나를 고르는 기준
- 화면별 최우선을 정한다. 최소 범위: 홈의 상태별(`docs/화면구성.md` 4절 표와 실제 코드의 상태), 목표 정하기 1~3, 학습 시작 전 이유, 학습 A/B/C, 회고, 완료, 기록.
- 처음 안내는 별도 투어보다 **그 자리의 블록**으로 푼다. 예: 처음 볼 때만 보이는 한 줄 설명, 빈 상태가 앞으로 무엇이 채워지는지 말하기, 첫 학습 전 홈의 오늘 흐름 미리보기. A단계 막힘마다 어느 블록으로 푸는지 연결한다.
- HTML 데모를 만든다. 지금 화면과 제안 화면을 나란히 둔다. 우리 3색과 글꼴을 그대로 쓴다. 오너가 브라우저로 볼 수 있게 경로를 알려 주거나 Artifact로 올린다.
- 오너가 고르게 한다. 화면별로 채택, 수정, 보류.

### C. 규칙 누락 점검 (프로젝트 스킬 두 개)
- 두 스킬은 `.claude/skills/`에 있다. 각 SKILL.md 맨 위 "그래고 프로젝트 우선 규칙"을 먼저 읽고 지킨다. 새 색, 글꼴, 그림자, 글로우, 이모지는 쓰지 않는다.
- `ui-ux-pro-max`: 저장소 루트에서 `PYTHONIOENCODING=utf-8 python .claude/skills/ui-ux-pro-max/scripts/search.py "<질의>" --domain ux` 또는 `--stack react-native`. 한 번에 한 관심사, 2~5단어로 묻는다. `references/pro-rules.md`의 Pre-Delivery Checklist를 합의안에 대어 본다.
- `mobile-app-ui-design`: Anti-Patterns 목록과 "Personalization by User Stage"를 합의안에 대어 본다.
- 결과물: 합의안에서 빠진 규칙 목록(규칙, 어긋나는 화면, 고칠 방법). 기존 체계와 부딪치는 권고는 따로 적고 따르지 않는다.

### D. 구현과 검증
- 합의된 항목만 고친다. 항목마다 계획을 먼저 쓴다: `1. [항목] → 검증: [확인 방법]`.
- 같은 역할의 부품은 같은 모양으로, 다른 역할은 다른 모양으로 둔다. 새 부품이 필요하면 `src/components/`에 두고 갤러리(`src/app/dev/gallery.tsx`)에도 올린다.
- 화면 문구는 `src/lib/copy.ts`에 둔다. `copy-tone` 스킬을 먼저 불러온다.
- 상태별로 렌더가 달라지면 단위 테스트(`src/lib/__tests__/`)나 선택자 테스트를 추가한다.
- 고친 화면을 다시 캡처해 전후를 나란히 보여 준다(`scripts/e2e/ui-states.py`, `docs/화면상태/`).
- 끝나기 전에 `npm run typecheck`, `npx expo lint`, `npm test`, `npm run check:static`을 돌린다.
- 기능 단위로 커밋한다. 메시지 끝에 저장소 규칙의 Co-Authored-By 줄을 붙인다. 푸시는 오너에게 묻는다.
- `docs/결정로그.md`에 결정을, `WORK_LOG.md`에 작업 기록을 추가한다.

## 4. 실행 환경

- 웹으로 볼 때: `.env.local`이 지금 **운영 Supabase**를 가리킨다. 운영 데이터를 바꾸는 테스트는 오너에게 묻는다.
- 로컬로 볼 때: Docker Desktop을 켜고 `npx supabase start`. 가짜 AI는 `AI_FAKE=1` 한 줄 env 파일로 `npx supabase functions serve --env-file <파일>`. `.env.local`을 로컬 주소(`http://127.0.0.1:54621`, 로컬 anon 키는 `npx supabase status`)로 바꾸고 `npx expo start --web --port 8081`. 운영 값은 백업해 두고 끝나면 되돌린다. 자세한 절차는 `WORK_LOG.md` "로컬에서 직접 확인하는 법".
- 로컬 데모 계정은 `review@graego.app`, 비밀번호는 `WORK_LOG.md`에 있다.
- Metro가 수정을 못 읽는 일이 있었다. 화면이 안 바뀌면 `--clear`로 다시 띄운다.
- `ios/`, `android/` 폴더를 만들거나 고치지 않는다.

## 5. 하지 말 것
- 레퍼런스 앱 화면을 보지 않고 "듀오링고는 이렇게 한다"고 쓰지 않는다.
- 디자인 체계(3색, 평면, 글꼴)를 바꾸지 않는다. 바꿔야 한다고 판단하면 근거와 함께 제안만 한다.
- 합의 안 된 화면을 같이 고치지 않는다. 발견하면 목록에 추가만 한다.
- 격려를 늘리는 방향(축하 효과, 칭찬 문구)은 기획서 원칙과 부딪친다. 제안할 때는 그 충돌을 같이 적는다.

## 6. 첫 메시지

A단계부터 시작한다. 시작할 때 오너에게 두 가지만 묻는다.
1. 가장 먼저 고치고 싶은 화면(추천: 첫 학습 전 홈, 목표 정하기)
2. 앱을 직접 띄워서 볼지, 기존 캡처로 볼지
